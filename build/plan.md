## 2. Principles for the exercises

1. **The exercise is the Wordle; the demos are not.** Slides and demos keep their own neutral examples (the physicists, the cars table, the planets), so an exercise never re-types a demo. The exercise applies the module's idea to the game.
2. **Every exercise starts with a reason.** A bug, a missing feature, a question the game cannot answer yet. Exercise 5 opens with the duplicate-letter bug that the naive Exercise 4 scoring has had since Exercise 2.
3. **Every exercise ends with a playable game.** No exercise leaves the project broken between steps for longer than one step.
4. **Tests are handed out from Exercise 5 on**, as the student's safety net. Students write their first tests themselves in Exercise 8 or 13 (section 10, Q8), as plain `assert` functions.
5. **★ steps teach a mechanism, ★★★ steps test understanding.** Roughly one ★, two or three ★★, one ★★★ per exercise, plus an optional **If time permits** at the end with no reference solution.
6. **Reference solutions are complete and run.** Each `solutions/NN-name/` is a uv project that passes `uv run pytest`, `ruff check`, and (from Exercise 12) `mypy`.
7. **Names are a contract.** The function, module and class names in section 4 are fixed, because starters, handouts, tests and the exercise text all refer to them. Change one only by changing all four.
8. **No dictation of whole files.** The longest ★ block in an exercise is around 20 lines.
9. **Text follows `AGENTS.md`** : businesslike full sentences, ` :` before a list, no em-dashes on bullet lines, every fence tagged, PEP 8 throughout.

## 6. Teaching properties without the confusion

The old order was : Java-style `get_length`/`set_length`, then
`length = property(get_length, set_length)`, then the decorator. Three syntaxes
for one idea, and the first one is the thing the course then tells you not to do.

The new order, on four slides in module 11 and Steps 3 and 4 of Exercise 11 :

1. **Attributes are public and that is fine.** `self.length = length`. Read it, write it. No accessors.
2. **A computed attribute.** `area` depends on `length`. As a method it is `sq.area()`. With `@property` above the `def` it is `sq.area`, always current, read-only. One decorator, no setter.
3. **When a plain attribute is not enough.** Show the bug : `sq.length = -3` is accepted. The fix is to make `length` a property with a setter that validates, storing the value in `self._length`. The code that uses the class does not change. That is why Python does not need accessors written in advance.
4. **The rule of thumb.** Start with a plain attribute. Turn it into a property the day it needs a rule. `_length` is the property's private storage, by convention.

`property(get, set)` and descriptors move to Advanced Python (its module 1 already
has `Property Syntax`). The demos `05_propertysyntax.py` and `06_classproperties.py`
are rewritten to match, as one demo per slide.

## 11. The exercise site (D12)

### What the PySpark course has

`../PySpark/build/site/` (about 2 400 lines of TypeScript, JS and CSS, plus 1 900 of
PySpark-only animation) builds one static HTML page per exercise guide. Each page opens
from disk with no server and no network : CSS, JS and the logo are inlined, links
are relative. Seen on `04-classes.html` :

- a sidebar with a progress bar and the steps, each with a Done count
- `###` is a step and `####` a sub-step (`1a`, `1b`), each with its own Done tick
- `:::hint` blocks, several per step, revealed one at a time
- `:::output` : "Check your output", collapsed
- `:::solution` : "Show solution", collapsed
- a starter panel with copy buttons, "Open the slides of this module", and a slide
  title in italics in the prose (*Properties*) opening that slide in a dialog
- a theme picker, Easter eggs, a quiz page with a printable certificate
- an index page grouping the exercises, with a "Hints and solutions" badge

The same markup feeds the exercises PDF through the course's own wrapper
(`../PySpark/build/build-achmea.ts`) : a hint becomes a blockquote, an output block
becomes "Expected output :", and solutions are collected into a section at the back.

| `site.js` (progress, Done ticks, reveal, copy, theme), `site.css`, `themes.css` | yes | The storage key prefix `pyspark-site:` becomes the course slug |

| `:::` preprocessing for the PDF | yes | Lives in `build-achmea.ts`; moves into the template's `exercises.ts`, with a choice of solutions "at the back" (PySpark) or "next page" (today's `<details>` behaviour) |

### What changes here once WP0 lands

- **The tiers map onto the markup** :
  - ★ the code is in the step itself
  - ★★ a skeleton in the step, one or two `:::hint`, a `:::solution`
  - ★★★ signature and tests in the step, `:::hint` with the approach, `:::output`
    showing the test run passing, `:::solution`
- The tier goes in the step title as a badge. The syntax is to be agreed in WP0, for
  example `### Scoring a guess {★★★}`, rendered as a pill on the site and as stars in the PDF.
- Exercise 5 is converted from `<details>` to `:::` (WP-conversion, small).
- The italic slide reference (*Annotating a Function*) is used wherever an exercise
  leans on a slide.
- The starter panel shows the starter folder, the handouts folder and the commands
  (`uv run python -m wordle`, `uv run pytest`) with copy buttons.
- **Release** : the site joins the release assets and the student bundle (`site/`,
  open `index.html`). In Codespaces it is opened through the editor's preview or
  `python -m http.server`.
- **A PRG400 quiz** (optional, Q12) : 30 to 40 questions across the modules, with the
  certificate. A good end-of-day-4 closer for a small group.
- The PDF keeps solutions on the next page, not at the back : students flip, they do
  not hunt (Q13).
